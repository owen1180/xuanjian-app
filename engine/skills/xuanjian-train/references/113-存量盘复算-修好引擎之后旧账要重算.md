# 一百一十三、存量盘复算：修好引擎之后，旧账要重算

> 配套脚本：`skills/xuanjian-archive/scripts/audit_charts.py`（自检 33 条）。
> 上一册 `TR112` 修了 `pillar.py` 的**夜子时双重进位**，并在待办第一条写下
> 「出生时刻 ≥23:00 的盘，时柱可能全错一天，须回查」。本册是那条待办的执行结果，
> 以及执行时撞出来的两件更值得记的事。

## 一、修 bug 不等于修数据

`TR112` 修的是**引擎**。改完之后，新排的盘是对的，但**已经出过的盘不会自己变对**：
档案卡片上写着四柱，报告 HTML 里写着断语，都是按旧引擎算的。修完 bug 就收工，
等于把错误永久固化在档案里。

所以「改了引擎」这件事必须配一个动作：**回头把所有存量盘用新引擎重排一遍，与归档比对**。
这不是敬业问题，是流程缺一环——缺了这一环，任何一次引擎修正都只能保证「以后对」。

`audit_charts.py` 就是这一环。它做四件事：

1. 从每张 `档案卡片.md` 抽出出生信息（公历年月日、钟表时刻、出生地经度、性别）；
2. 用 `pillar.py` 的口径重排（真太阳时只做经度修正；过 23 点日柱进一天、时柱走五鼠遁）；
3. 与**目录名上的四柱**逐柱比对；
4. 报「一致／四柱不一致／无法复算」，并单独报**时辰交界距离 ≤30 分**的盘。

## 二、三条纪律

**① 不代改档。** 脚本只报，改不改、怎么改由主理人定。四柱是档号，改一个字要动目录名、
索引页、关联卡片三处链接，机器不该自己动手。

**② 抽不到就报，不许默认。** 缺经度**不默认 120**（那等于替人搬到东经 120 度出生）；
时刻只给了时辰区间（「巳时 9:00–11:00」）**不取中点**（那等于自己编一个出生时间）。
一律进「无法复算」并写明缺什么。**静默兜底比不查更坏**——它会产出一份看着通过的结论。

**③ 边界要报警。** 真太阳时距时辰交界 ≤30 分钟即报：这类盘不是错，是「再报错一次出生
时间就换时柱」。它悬着，人得知道它悬着。

## 四、「21 分钟现象」：桂林整点出生必然贴边界

四盘桂林、都报整点（10:00／16:00／18:00），真太阳时都落在交界后 **21 分**。
不是巧合：桂林东经 110.29，经度修正 −38.8 分，取整 −39 分；整点减 39 分 = 交界前 21 分。

**这条对报时精度的要求比想象中硬**：客户报「大概十点」，误差只要超过 21 分钟，
时柱就从中段翻到上段；一盘要重排、紫微十二宫要重排、断语要重写。
所以档案里那句「钟表 15:00–15:39 时段，真太阳时会落未时」不是谨慎，是必须写。

## 五、假绿：判词是真的，校验是假的

第一版审计器给某张卡片判了「一致」，理由看着很硬：真太阳时 09:00，巳时，与归档相符。
**但那张卡片根本没写出生钟点。** 09:00 是从哪来的？

——从卡片另一行：「- 时辰边界：北京时间 9:39 为辰/巳分界」。
原实现把这一行也当「出生行」扫了，抓到 9:39，减 39 分得 09:00，正好落在巳时，
于是与归档「相符」，判一致。

**这是比漏查更难发现的一种错：判词是对的，校验是假的。** 结论恰好正确，
所以没人会去翻它的算式。而它一旦遇到真正的错误盘，同样会给出「一致」。

修法是把抽取范围收紧到「出生／公历／钟表」行，并**排除**含「真太阳时／交界／分界／
修正」的行；抽不到就判「无法复算」。宁可少核一盘，不可假核一盘。

另外两处同类修正：
- 性别不能全篇搜「坤造」——档案卡片会写「关联：1957 坤造（母）」，乾造盘会被判成女。
- 「巳时（9:00–11:00）」这种区间不取中点。区间给的不是时刻。

## 六、另一件顺带查出来的事：提案编号不稳定

`TR110` 留下的待办「`distill` 应过滤问句」，这次去动它之前先查了 id 生成方式：
`ruling.py` 用 `enumerate(条, 1)` 生成 `D%03d`，**是位置号，不是内容号**。

这意味着：只要 `distill` 少提一条（比如把问句过滤掉），后面所有提案的编号全部前移一位。
而台账里已有 **51 条裁决**（`D001`–`D226` 范围），它们指向的会是**别的提案**——
裁过的东西静默错位，且无法察觉。

**所以这条待办不是一行过滤能修的。** 正确次序是：先给提案加**内容指纹**（去重后的文本哈希）
当稳定 id，让台账按指纹挂靠；再改过滤。次序颠倒，等于把 51 条裁决作废。

这就是「待办看起来很小」的典型：它真正缺的不是代码，是**先稳住编号**。

### 六·补 已修：指纹落地，量化出「会错位 52 条」

2026-11-05 当日就把次序按正确顺序走完了：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | `distill.py` 每条提案带 `fp`（归一后 md5 前 8 位） | 223 条全部有指纹 |
| 2 | `ruling.py 载提案` 有指纹用指纹（`D-<fp8>`），无才退回位置号 | 位置号留作 `id_legacy` 备查 |
| 3 | 新命令 `迁指纹`：**按正文匹配**，把台账旧 id 换成指纹 | **60 条全换，0 未匹配** |
| 4 | 新命令 `核对`：每条裁决的 id 必须指回「提案正文以裁决正文开头」的那一句 | **60 条，错位 0** |
| 5 | 此时才加问句过滤并重跑 `distill` | 提案 226→**223**，跳过问句 3 条 |

**如果把第 5 步提前，代价是多少？** 拿改动前的备份逐条算：

> 裁决 60 条：**位置号会错位 52 条**／位置不变 8 条／提案已不存在 0 条。

不是三五条，是**五十二条**。原因是这一轮册库也变了（`57` 册补了兜底规格），
`对撞` 结果整片位移——位置号从一开始就不该用来挂裁决。

三条纪律随之补上：

- **id 跟内容走**。提案换序、增删、重跑，指纹都不变；`D-<fp8>` 才是「哪一条」。
- **迁移按正文，不按序号推**。台账每条都存了当初裁的原文，拿它对提案表匹配，
  与「现在是第几条」无关；匹配不到就标 `fp_missing` 留着让人看，不许静默丢掉。
- **核对要能独立跑**。指纹只保证「同内容同号」，保不了「台账没被手改过」，
  所以另有一条 `核对`：id 指不回原句就红。
