# 六十七、星曜—宫位—病症实体建模与语料源清单

> 这一册做两件事：**把"星曜↔宫位↔病症"建成可检索的实体关系**，以及**把本馆能用的外部语料从哪来、是什么、能不能商用列成一张清单**。
> 实体建模方法取自 `zenoyang-ai/nihaixia-knowledge-graph`（星曜—宫位—病症知识图谱）；语料源清单方法取自 `Lance-myk/Traditional-Chinese-Medicine-nihaisha`（全套视频／PDF 语料来源清单）。
> 与 `65`（判语级溯源）、`66`（证据分层）、`63`（经方）、`25`（望诊）、`11`/`15`（紫微）配套使用。

## 1. 为什么要这一册

之前各册是"人读的方法论"，这一册要补的是"机器可检索的结构"：

1. **星曜—宫位—病症** 三者目前散落在 `11`/`15`（星性、宫位）、`25`/`26`（望诊、调摄）、`63`（方证）里，没有一处把"某星落某宫 → 对应哪一脏、哪一体、哪一类身体提醒"连起来。
2. **外部语料从哪来** 在 `64` §6 讲了许可，但没列"具体有哪些源、各是什么格式、要不要进插件包"。

本册把它们各归一类，给后续建库、建索引、建图谱打底。

## 2. 星曜—宫位—病症实体模型（借 `zenoyang-ai/nihaixia-knowledge-graph`）

知识图谱把"看盘 → 望诊 → 经方"串成一张实体—关系网。本馆照其**结构**落地（不照搬其数据，数据只放工作区）：

### 2.1 三类核心实体

| 实体 | 内容 | 本馆落点 |
|---|---|---|
| **星曜（stars）** | 十四主星＋六吉六煞＋四化 | `11` §3–§4、`15` §1 取象 |
| **宫位（palaces）** | 十二宫（命／兄／夫／子／财／疾／迁／友／官／田／福／父） | `11` §2 十二宫主事 |
| **病症（symptoms）** | 五脏开窍、五体、五志、五色所主的身体信号 | `25` §3 五脏相应、`26` §7 六健康标准 |

### 2.2 关键关系（建库时照此连边）

```
star --[落于]--> palace            # 某星落某宫
palace --[主]--> organ             # 宫位对应脏（疾厄→身体整体；其余宫位按星性推）
organ --[开窍于]--> orifice        # 肝开窍于目、心开窍于舌……
organ --[其华在]--> body_part       # 肾华在发、肺华在毛……
organ --[在志为]--> emotion         # 怒伤肝、喜伤心……
symptom --[归]--> organ             # 某信号归某脏
formula --[主]--> syndrome          # 方证对应（见 63 §9.1）
```

> **修正注（据 `70` §1，天纪 `05-illness` @00:44:35 起）**：上面"疾厄→身体整体／按星性推"是**早期简略写法**。倪师明确说"斗数上面的疾厄宫，参考可以，真的批的时候他就没有用""七杀在疾厄宫代表痔疮，这个不重要"。**正确顺序**：① 先看全盘、找最差的宫（两宫皆差则两脏兼病）；② 用歌诀「肺寅大卯胃辰宫，脾巳心午小未中，申膀酉肾心包戌，亥焦子胆丑肝通」把疾厄宫**地支**对到脏腑；③ 疾厄宫无星 ≠ 无病；④ **落到病名级排查、不落诊断**（`OB100` §3.4）：按地支脏腑给 2–3 个病名＋检查项，写「需排查」，不写「你这是」。
>
> 下面的链条示例**只作"链路结构"演示**；具体落到哪个脏腑，须改用歌诀按地支定位，不可按星性硬对病。

### 2.3 一个完整链条示例（紫微 → 望诊 → 调摄）

```
巨门（星）落疾厄（宫）且陷
   → 巨门在疾厄主"暗疾、郁滞"（11/15 取象）
   → 落陷则"门一直关着"，对应情绪压抑、消化隐疾
   → 望诊侧：舌暗、面色偏暗（25 §2）
   → 调摄侧：疏肝理气方向、少甜少冰（26 §3）
   → 不落病名、不开方、不劝停药（24 红线）
```

**这条链的用法**：当斗枢（紫微）指出"某星落某宫有某倾向"，明相（望诊）与南阳（经方）可以**沿同一实体链给身体提醒与调摄方向**，但三者都只到"提醒／方向"为止，不互相当证据。

### 2.4 与审计设施的衔接

`65` §5 的 SQLite 三层已预留 `stars`／`palaces`／`patterns`／`judgments`／`classics` 实体与 `star_palace`／`pattern_star`／`judgment_src` 关系表——本册 §2.2 的关系即在那张表里落地。

### 3.1 源清单的三条纪律

1. **清单之外的源，不进库**。新增语料先登记到本表，再决定进哪个库（tianji／renji／其他）。
2. **每条语料必须能归因到本表某一行**，否则进 `65` §5 的 `ingestion_quarantine` 隔离，不污染主库。
3. **商用红线**：以上全部非商用。插件对外只交付"检索结果 + 出处链接 + 证据层标注"，绝不含语料全文或衍生商用内容。

1. **实体表骨架**：在审计 SQLite 中建 `stars`／`palaces`／`symptoms` 三表与关系边（沿用 `65` §5 设计）。
